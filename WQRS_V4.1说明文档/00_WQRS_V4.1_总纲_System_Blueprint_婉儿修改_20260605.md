## 系统定位

一个基于宏观状态自适应、严格风险预算、以及机构级算法执行的个人量化投研与自动化交易框架。

**核心信仰：风控优先于收益，概率胜于预测，纪律战胜人性。**

## 一、系统全局拓扑与职责边界

WQRS 采用自上而下的六层漏斗架构，模块之间单向解耦，通过标准 JSON 协议传递指令，**严禁下层模块越权修改上层风控参数**。

| 模块层级 | 核心组件 | 系统职责 | 输入 | 输出 |
|---|---|---|---|---|
| 1. 哲学层 | Ch01 投资哲学 | 确立系统价值观与不交易原则 | 市场底层数据 | 绝对生存红线 |
| 2. 宏观层 | Ch02 宏观引擎 | 总闸门：判断市场状态，决定总敞口 | 高低频宏观/流动性因子 | 仓位硬上限（如 80% 或 0%）|
| 3. 资产层 | Ch03 资产配置 | 资金分配：跨容器风险平价 | 宏观状态与上限 | 各容器资金预算 |
| 4. 中观层 | Ch04 行业轮动 | 寻矿器：剔除拥挤赛道，寻找资金景气共振 | A容器资金预算 | 目标行业清单与预算；**dropped_sectors 列表** |
| 5. 微观层 | Ch05 基本面引擎 | 排雷网：财务一票否决，综合打分 | 目标行业内个股池；**dropped_sectors 订阅** | 绝对干净的个股白名单（含状态字段）|
| 6. 战术层 | Ch06 信号引擎 | 发令枪：识别突破信号，管理 A/B/C 三容器信号 | 个股白名单；**含 whitelist_status** | 精确买卖信号；**含 signal_quality_score / historical_win_rate / historical_rr_ratio / b_adjusted_for_limits** |
| 7. 算力层 | Ch07 仓位管理 | 弹药库：凯利压缩 + 体制转换检测，精确算股 | 买卖信号（**含质量字段与赔率修正**）与风险止损 | 具体下注股数（100股对齐）|
| 8. 执行层 | Ch08 状态机 | 终结者：GTSM 全局状态机（含退出条件），冰山拆单，T+1 锁定 | 合规交易 JSON；**EMERGENCY_OVERRIDE 通道** | 实盘订单 API 路由与成交审计日志 |

## 二、系统级绝对风控红线

> 以下红线必须写在底层拦截器（Interceptor）中，任何逻辑违反即触发内核级熔断。

### 暴露度控制红线

- **单笔风险熔断**：单笔交易最大绝对损失 ≤ 总资产净值的 **1%**
- **个股集中度**：单一股票名义本金总暴露 ≤ 总资产净值的 **10%**
- **行业集中度**：单一申万一级行业总暴露 ≤ 总资产净值的 **30%**
- **未脱险总敞口**：处于浮亏或止损未上移至保本线的总仓位风险 ≤ **5%**

### 物理执行与数学红线

- **凯利压缩原则**：`W_adjust` 仅做向下压缩，约束范围强锁在 **[0.1, 1.0]**，绝不允许放大 1% 初始风险
- **凯利输入来源**：`W_adjust` 必须由 Ch06 输出的 `signal_quality_score`、`historical_win_rate`、`historical_rr_ratio`、`b_adjusted_for_limits`（V4.2 新增）四个字段驱动计算，**禁止使用固定值**
- **凯利五层保护体系（V4.2 新增）**：
  1. Half Kelly（减半压缩）
  2. clamp [0.1, 1.0]（防止极端值）
  3. 分容器独立统计（A/B/C 各自维护胜率池）
  4. **体制转换检测**：近 30 日胜率与近 90 日胜率偏差 > 1.5σ 时，W_adjust 附加 ×0.7 折扣
  5. **赔率截断修正**：止损价触及跌停线时 b×0.80，目标价触及涨停线时 b×0.90
  6. **最大下注上限**：单笔名义本金 ≤ 总资产的 3%，无论凯利公式输出多少
- **物理手数量化**：最终执行股数必须是凯利调整后 `floor(shares / 100) × 100`
- **动态均价止损**：金字塔加仓后，止损线必须上移至 `max(初始止损价, 最新动态加权成本均价)`

### 加仓决策边界红线（V4.1 新增，V4.2 维持）

- **Ch06 职责**：仅输出 `add_position_permitted: true/false`，**禁止在 Ch06 中定义加仓比例数字**
- **Ch07 职责**：加仓股数的全部计算权力归 Ch07，Ch06 的 YES/NO 是唯一触发条件

## 三、全局异常与黑天鹅响应矩阵（V4.2 修订版）

| 异常触发场景 | GTSM 指令与系统动作 |
|---|---|
| 个股封死涨停（price ≥ limit_up）| 拒绝排队，放弃 VCP 突破信号，直接撤单归档，防炸板诱多 |
| 个股跌停开盘 — 隔夜持仓（price ≤ limit_down）| 绕过冰山拆单，09:29:59 用跌停价全仓抢跑集合竞价队列，断臂求生 |
| 个股跌停开盘 — 当日买入（T+1 锁定）| **无法卖出（T+1 制度限制），标记为「T1_LOCKED」，加入次日抢跑队列，第二天 09:29:59 自动执行** |
| 盘中闪崩跌停 — 隔夜持仓 | 立即市价/跌停价清仓，绕过正常止损链路 |
| 盘中闪崩跌停 — 当日买入（T+1 锁定）| **无法卖出，标记次日抢跑，写入审计日志 T1_LOCKED** |
| 系统性闪崩（指数 30 分钟跌 > 2.5% 或多于 3 只同步跌停）| 全局买入与加仓接口物理断电；GTSM 注入 **EMERGENCY_OVERRIDE** 信号，接管 Ch07 输出权限；**触发后持续 ≥ 30 分钟，且满足 4 项退出条件时自动解除，进入 30 分钟观察期后恢复** |
| EMERGENCY_OVERRIDE 退出（V4.2 新增）| 满足全部退出条件（30分钟+指数回升≥50%+跌停≤1只+无新增）→ 进入 POST_EMERGENCY 观察期（30分钟，仅B/D容器）→ 自动恢复 NORMAL；支持 `force_override_clear` 人工强制解除 |
| 柜台软失败（滑点过大或未成交）| 撤单并采用进攻性滑点补偿重新挂单，最多重试 **3 次**，超限即 DEAD_ORDER |
| 柜台硬失败（非法单位/资金不足）| 绝对禁止重试，抛出致命异常直接写入 DEAD_ORDER |

## 四、核心数据流与执行时钟（V4.2 修订版）

| 时段 | 名称 | 系统行为 |
|---|---|---|
| 盘后结算（15:30–18:00）| 数据刷新期 | AKShare 拉取全市场日线、财务、宏观数据；驱动 Ch02~Ch05，更新次日宏观预算、目标行业与个股白名单 |
| 盘前竞价（09:15–09:25）| 竞价准备期 | 监控突发跌停黑天鹅，标记隔夜持仓抢跑队列及 T+1 锁定次日抢跑队列 |
| 集合竞价（09:25–09:30）| 竞价执行期 | 仅执行隔夜跌停抢跑单 + T+1 锁定次日抢跑单，不参与正常竞价博弈 |
| 极速止损期（09:30–09:45）| 止损专用窗口 | **仅允许隔夜持仓止损单执行（含跌停抢跑），禁止一切新开仓（含突破追价）** |
| 噪音过滤期（09:45–10:00）| 缓冲观察期 | 禁止所有新开仓，等待价格结构稳定 |
| 隐蔽潜行期（10:00–14:30）| 正常交易期 | 开启 TWAP/VWAP 大资金建仓路由，拆单间隔 3000ms–7000ms |
| 尾盘清扫期（14:50–14:57）| 强制出清期 | 撤销所有 PARTIAL_FILLED 残单，用集合竞价跨价单完成终极出清 |

> **V4.2 核心变更**：消除了 Ch00 与 Ch08 的窗口规则矛盾。原「极速攻击期 09:30-09:45 允许突破追价」与「禁止交易窗口 09:30-10:00」冲突，现统一为：09:30-10:00 全程禁止新开仓（含突破追价），仅 09:30-09:45 允许隔夜止损单执行。

## 五、EMERGENCY_OVERRIDE 状态机闭环（V4.2 新增）

### 状态转移

```
NORMAL ──[Flash Crash 触发]──▶ ACTIVE
                                 │
                    [30min + 4条件全满足]
                                 │
                                 ▼
                          POST_EMERGENCY
                         │              │
             [30min无事]  │              │ [再次触发]
                         ▼              ▼
                       NORMAL         ACTIVE

任意状态 ──[force_override_clear]──▶ NORMAL（人工豁免观察期）
```

### 触发条件（不变）

1. 沪深 300 30 分钟内跌幅 > 2.5%
2. 或持仓中 > 3 只个股同步触发跌停

### 退出条件（V4.2 新增，全部满足时自动进入 POST_EMERGENCY）

1. 距离最近一次 EMERGENCY_OVERRIDE 触发 ≥ 30 分钟
2. 沪深 300 较触发时点价格回升 ≥ 50%（收复一半以上失地）
3. 跌停个股数量 ≤ 1 只
4. 无新增跌停触发

### POST_EMERGENCY 观察期规则

- 30 分钟观察期
- 仅允许 B 容器（股息价值）+ D 容器（现金）操作
- A 容器（权益增长）和 C 容器（宏观对冲）继续冻结
- 观察期结束后自动恢复至触发前宏观状态
- 观察期内再次触发 → 直接回到 ACTIVE，计时器重置

### 人工强制解除

`force_override_clear` 指令直接清除接管状态至 NORMAL，跳过观察期。仅限授权通道发送。

## 六、T+1 跌停抢跑分层机制（V4.2 新增）

A 股 T+1 制度下，当日买入的股票当日无法卖出。跌停抢跑逻辑需区分持仓天数：

| 异常场景 | 当日买入（holding_days = 0） | 隔夜持仓（holding_days ≥ 1） |
|---------|---------------------------|----------------------------|
| 跌停开盘 | 无法卖出，标记 T1_LOCKED，次日 09:29:59 抢跑 | 09:29:59 跌停价全仓抢跑 |
| 盘中闪崩跌停 | 无法卖出，标记 T1_LOCKED，次日 09:29:59 抢跑 | 立即市价/跌停价清仓 |
| 连续跌停（次日继续） | 再次标记，继续排队次日 | 首日已抢跑，剩余仓位继续抢跑 |

**制度性对冲措施（降低 T+1 锁定概率）**：
1. 建仓时点保护：新开仓全部在 10:00 之后，回避开盘跌停窗口
2. 仓位控制：首笔建仓仅 30% 目标仓位，单笔上限 1% 风险
3. 宏观过滤：Risk Off/Panic/Capitulation 状态下禁止新开仓
4. 质量筛选：Ch05 Hard Filter + Accounting Red Flag 过滤高风险标的

## 八、数据工程规范（V4.2 补充）

### 数据库方案

使用 **SQLite + WAL 模式** 作为主数据库：

- 启用 WAL（Write-Ahead Logging）模式：`PRAGMA journal_mode=WAL`
- 年增量预估 < 500MB（全市场日线 + 财务 + 宏观），SQLite 轻松承载
- 单机单进程访问模式，无并发竞争
- 备份策略：每日盘后自动复制 `.db` 文件至备份目录
- 迁移路径：使用 SQLAlchemy ORM 编写数据访问层，如需升级至 PostgreSQL 时迁移成本可控

### JSON 协议版本化（V4.2 新增）

所有模块间 JSON 输出必须包含 `protocol_version` 字段：

```json
{
  "protocol_version": "4.2",
  "module": "ch02",
  ...
}
```

下游模块在处理前检查版本号，若版本不匹配且无法兼容，应拒绝处理并写入审计日志。
